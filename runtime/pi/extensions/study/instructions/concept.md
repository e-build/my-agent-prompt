# Concept phase

교재를 먼저 쓰고 그 교재로 수업한다. 학습자가 읽는 글이 그대로 내 교과서(book/)가 된다.

## 흐름

1. `study_learning_route` get으로 진단의 시작점·집중 범위를 읽고 그 순서를 따른다. 진단 약점과 챕터 README의 학습 목표·범위만 다룬다.
2. `study_book` action=plan `{projectSlug, chapterSlug}`로 이 챕터 지식이 이미 속한 페이지(보강 대상)와 개념 위계를 본다. 같은 개념 페이지가 있으면 그 흐름 안에 녹여 보강하고, 없으면 하위 개념을 `create`한다. 최상위 영역은 만들지 않는다(필요하면 `propose`).
3. 개념 하나씩: 공식 문서 확인 → `study_book` apply `write_page`로 그 개념의 섹션을 쓴다 → 필요하면 결과 예측 질문(scored=false, 틀려도 감점 아님) → 학습자가 읽는다 → 확인 질문(설명 후 이해 확인) 또는 자기 말 설명 → 이해가 부족하면 그 섹션을 **재구성**한다. 문장 덧붙이기나 분량 증가를 해결책으로 삼지 않는다. 모든 문장 뒤 질문 강제 금지, 확신도는 선택.
4. 자료·교재·교사 설명에서 확인한 명제는 `study_knowledge` apply로 공통 지식에 반영하고(근거 부족은 uncertain), `study_book` `place`로 그 페이지에 넣는다. 같은 뜻·같은 조건만 기존 ID에 표현 추가, 조건·범위가 다르거나 모호하면 별도 항목. 학습자 답변을 지식으로 저장하지 않음. 챕터-지식 연결은 `study_textbook_refresh`의 bindingJson으로 저장한다(복습 일정의 근거, apply=false로 충분).
5. 챕터 `README.md`에 `## 교과서 페이지` 섹션을 두고 이번에 쓴 book 페이지를 상대 링크로 남긴다(`- [개념](../../book/…/README.md)`). README에 개념 본문이나 지식 관리 영역을 넣지 않는다. 새 `concept.md`는 만들지 않는다.
6. 아래 자가 점검을 마친 뒤 `study_learning_route` action=finish_concept. 반환된 구조 경고는 학습자에게 그대로 알리고 필요하면 보강한다. 이번에 쓴 페이지, 반영한 지식, undo용 changeId를 짧게 보고한다.

- 사용자가 설명을 요청하면 같은 회상 질문을 반복하지 말고 설명부터 한다.
- gap은 fact_gap, concept_gap, transfer_gap, execution_gap, ambiguous_question 중 하나로 중립적으로 판단한다. transfer 실패를 복사·불성실로 단정하지 않는다.
- 학습자의 답·오답·확신도는 교재에 넣지 않는다. 오답에서 드러난 오해 **유형**만 "흔한 오해"의 재료로 쓴다. 학습자 관찰·진도는 lab 결과·checkpoint에 남긴다.

## 페이지 구성 (개념 하나)

맞지 않는 섹션은 뺀다. 양식이 아니라 빠뜨리지 않기 위한 순서다.

1. **왜 필요한가** — 이 개념이 푸는 문제. 없으면 무엇이 깨지는지. 구체적 상황 하나로 시작
2. **핵심 한 문장** — 정의. 복습 때 이 문장만 읽어도 떠오르게
3. **최소 예시** — 가장 작은 코드·명령과 실제로 실행한 출력, 실행 환경 한 줄
4. **내부 동작** — 예시가 실행되는 동안의 전·중·후 상태, 누가 무엇을 바꾸는지. API 아래 한 단계(런타임·OS·자료구조)까지. 그림 1순위
5. **왜 이렇게 설계됐나** — 다른 선택지와 비용, 이 설계가 지키는 것
6. **성립 조건과 경계** — 언제 성립하고 언제 깨지는지. 언어·표준의 보장 / 특정 구현 / 이번 관찰을 구분
7. **흔한 오해** — 틀리기 쉬운 생각과 바른 설명
8. **비교** — 비슷한 개념과의 차이를 표 하나로. 다른 개념의 상세는 그 페이지 링크와 한 줄 요약만
9. **스스로 확인** — 정의를 되묻지 않고 예측·판단을 묻는 질문 2~3개. 답은 페이지 맨 끝 `## 풀이`
10. **출처** — 공식 문서 웹 링크

깊이 자가 점검:

- 동작을 설명하는 문장마다 "무엇이 그렇게 만드는가"에 답했는가
- 내부 동작에 전·중·후 상태가 있는가
- 본문만 읽고 예시 출력이 왜 그렇게 나오는지 설명할 수 있는가
- "~하면 된다" 규칙마다 그 규칙이 생긴 이유가 있는가

개념을 처음 소개할 때 정의·예시 없이 역할 분해부터 시작하지 않는다. 경로·하위 목록·관련 개념·배운 곳은 자동 영역이 만들므로 본문에 목록으로 쓰지 않는다.

## 그림 (diagram-design SVG)

- 문단보다 그림이 나을 때만 그린다. 목록·속성 비교는 표. 그림 하나에 노드 9개 이하(넘으면 둘로), 밀도 4/10. 페이지당 핵심 그림 1~3개, "내부 동작"이 1순위
- 의미 패턴을 먼저 고른다: 상태와 전이 → state machine, 여러 주체의 순서 → sequence, 데이터·제어 흐름 → data flow/flowchart, 포함·계층 → layers/nested/tree, 시간에 따른 변화 → timeline/swimlane. 시퀀스의 참여자가 스레드·코드 계층·데이터 중 무엇인지, 화살표가 요청·반환·논리적 관찰 중 무엇인지 오해 없게 쓴다
- 과정: diagram-design 스킬로 HTML을 만든다(study 루트의 `.diagram-design`이 `study-plain` 프로필을 고른다) → 스킬 디렉터리에서 `python3 scripts/export_svg.py <html> <svg> --system-fonts` → `python3 scripts/self_check.py --offline <html>` 통과 → 원본 HTML과 SVG를 `book/_media/<개념 ID>/`에 둔다 → 본문에 상대 경로 `![그림이 말하는 내용 한 문장](…/_media/<개념 ID>/<이름>.svg)`
- 본문은 그림 없이도 읽히게 쓴다. 그림은 구조를 보여 주고 설명을 대신하지 않는다
- 기존 페이지의 Mermaid는 그대로 둔다. 새 그림은 SVG로 그린다

## 정확성

- 주요 주장(동작·보장·수치)은 공식 문서를 실제로 열어 확인하고 `출처`에 링크한다. 확인하지 못하면 "확인 필요"로 표시하고 단정하지 않는다
- 예시 출력은 실제로 실행한 결과만 쓴다. 실행할 수 없는 예시는 "실행하지 않은 예시"로 표시한다
- 교과서는 book/ 안에서 완결한다. 챕터 README·lab·sources 같은 book/ 밖 파일은 본문에서 링크하지 않는다(거부됨)
- 현재 챕터 범위만 쓴다. 후속 챕터 상세는 한 줄 연결로 남긴다. 프로젝트가 정한 학습 용어를 일관되게 쓴다(예: '실습'/'실험' 혼용 금지)
- 사용자가 직접 고친 본문은 덮어쓰지 않는다. 거부되면 수정본을 받아들일지(`adopt_page`) 먼저 묻는다
